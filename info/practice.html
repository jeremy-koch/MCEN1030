or is True if either side is True. And watch the last one closely: is −40 less than −40?

L3. Pipe flow is laminar below a Reynolds number of about 2300, turbulent above about 4000, and transitional in between. (Those are just three labels for three ranges of a number. No fluid mechanics needed today.) Predict what flow_regime(10000) returns, then fix the function.

10000 is greater than 2300. Once a branch is True, does Python ever look at the ones below it?

It returns "transitional". The turbulent branch can never run: anything above 4000 is also above 2300, and the first branch grabs it. Two fixes, either is fine:

# check the biggest threshold first
if Re > 4000:
    return "turbulent"
elif Re > 2300:
    return "transitional"
else:
    return "laminar"

or keep the original order but make the middle branch say exactly what it means: if Re > 2300 and Re <= 4000:. The first is more common. With elif chains, the order is part of the logic.

FN3. This is the checkpoint-style one: write the whole function from its spec. Try it on paper first, about five lines. Then, before you trust it, work out one case by hand where you already know the answer, and make sure the function agrees.

The spec: cost_to_run(power_W, hours, price_per_kWh=0.15) returns the cost, in dollars, of running a device that draws power_W watts for hours hours, when electricity costs price_per_kWh dollars per kilowatt-hour.

A kilowatt-hour is 1000 watts for one hour. So first turn watts into kilowatts, multiply by hours to get kWh, then multiply by the price. The easiest hand check is the one you can do without a calculator: a 1000 W device for 1 hour is exactly 1 kWh.

def cost_to_run(power_W, hours, price_per_kWh=0.15):
    """Dollars to run a device drawing power_W watts for `hours` hours,
    at price_per_kWh dollars per kilowatt-hour."""
    energy_kWh = power_W / 1000 * hours
    return energy_kWh * price_per_kWh

The hand check: 1000 W for 1 hour is 1 kWh, which costs $0.15. The space heater is 1.5 kW × 8 h = 12 kWh, so $1.80 (Python may print 1.7999999999999998, the same harmless decimal fuzz as in DI3).

The classic slip is forgetting the / 1000. Then one hour of a 1000 W device costs $150, and the space heater costs $1800 a night. Nobody’s electric bill looks like that… which is exactly why the hand check catches it, without anyone having to stare at the code.

Looping over values, looping over indices · P4

X1. Fix the loop so it prints the sum of the squares of 1 through 4. (What value do you expect?)

Run it as-is and look at what you get: 16. The loop isn’t accumulating — each pass throws away the previous total. What’s missing from the right-hand side?

total = total + k * k

The accumulator pattern: the new total is built from the old total. total = k * k just overwrites, and you end up with only the last pass (16).

  1. Names must exist before they’re used.
  2. The indented line belongs to the for.
  3. The print needs everything finished.

(Also — could you avoid hard-coding count = 3? Python’s len(values) exists and is probably better.)

for v in values:

print(total / count)

The first three lines can go in any order among themselves.

X4. We have two parallel lists: the voltage and current of four devices. Fill in the blank so the loop prints each device’s power, \(P = VI\).

A for v in volts: loop would hand you each voltage… but then how would you find the matching current? The index i is the thing that ties volts[i] to amps[i]. How many indices do you need?

Prints 24.0 W, 6.0 W, 5.0 W, 0.66 W. This is the reason to loop over indices: you need the same position in two (or more) lists at once.

Loops with if inside · P4, A1

X7. A wind sensor logs -999.0 whenever it misses a reading. Fill in the condition so only the real readings get collected.

Several conditions work: “not equal to −999,” or “at least zero” (can a wind speed be negative?). sum and len are built into Python and work on plain lists.

if v != -999.0:      # or: if v >= 0:

good is [8.1, 10.7, 9.8, 7.4] and the average is 9.0 m/s.

Now try it with the if removed, so every value gets appended. The average comes out to −327 m/s: a wind blowing backwards at roughly the speed of sound. Nobody needs to read the code to know that’s wrong — which is the whole point of estimating before you trust a number.

X8. Counting is just an accumulator that adds 1. How many of these daily highs (°C) are above 32? Fill in the blank.

Same shape as total = total + x, but what are we adding each time we find a hot day?

hot_days = hot_days + 1

Prints 3 (33, 35, 34). Swap the 7 numbers for a century of Boulder summers and this is, more-or-less, one way to ask “are hot days getting more common?”

X9. The “best so far” pattern. Predict what prints. Then change output[3] to 320 (a tie!) and predict again. Then change > to >= and predict a third time.

Keep a table with one column: best_i. It only changes when the current output beats the best one so far. Does “ties” count as beating?

Original: 40 320.

With the tie and >: still 40 320. When i is 3, 320 > 320 is False, so the first 320 keeps its spot.

With the tie and >=: 50 320. Now a tie does count, so the later one takes over.

This is exactly what output.argmax() does for you in one line (and NumPy picks the first one on a tie, like >). Writing it by hand is worth doing once, because the loop version can do things argmax can’t, like “the best one we can afford.” See the last problem on this page.

X10. Here are positions logged during a phone drop (onto a pillow, please), every 0.1 s. The loop estimates the velocity between each pair of neighboring readings. Predict the printed values — roughly is fine — and figure out why the range starts at 1.

range(1, 5) is 1, 2, 3, 4 — it starts at 1 instead of 0. Each pass uses the reading at i and the one just before it, at i-1. What would i-1 be on a pass where i is 0?

0.1 -0.49
0.2 -1.47
0.3 -2.45
0.4 -3.44

A physics check: the velocity should get about \(g\,\Delta t = 9.81 \times 0.1 \approx 0.98\) m/s more negative every step, and it does (−0.49, −1.47, −2.45, …). Negative, because we measure \(y\) upward and the phone is going down. Good.

Why start at 1? If i were 0, then y[i-1] is y[-1], the last reading. Python happily does that (negative indices are legal!) and you’d get a “velocity” of about −1.96 m/s at t = 0, when the phone hadn’t started moving yet. No error, just a wrong number. (Also notice that five positions give only four velocities. Off-by-one, our old friend.)

Simulation (week 5) · S1, S3

SIM1. A cup of coffee cools faster when it’s much hotter than the room, and slower as it gets close. A time-stepped version: each minute, the temperature drops by a fraction k of the gap between the coffee and the room. Trace it and predict the three printed lines.

First pass: the gap is 90 − 20 = 70, and 10% of that is 7. The second pass starts from wherever the first one left off.

0 83.0
1 76.7
2 71.03

The drops are 7, then 6.3, then 5.67: shrinking, because the gap shrinks. That’s the “slows down as it gets close” behavior we wanted.

SIM2. Now let’s break it on purpose. Same cooling model, but someone got impatient and took fifteen-minute steps. Run it. What’s wrong with the answer, physically?

Look at the first printed temperature. Can coffee sitting in a 20 °C room get colder than the room?

0 -15.0
1 37.5
2 11.25

Frozen coffee, in a warm room, which then bounces back up to 37.5 and down again. A real cup never goes below room temperature. The algebra is fine. The problem is that k * dt is now 1.5, so each step “removes” 150% of the gap and overshoots. Small steps keep the model honest. (Try dt = 5.0: it’s off from the dt = 1 answer, but at least it’s not absurd.)

SIM3. After a falling-ball simulation, we want the time when the ball first goes below the ground. Fill in the blank, using a mask from week 4 (no new loop needed).

Build it in pieces. y < 0 is an array of True/False. t[y < 0] is every time when the ball was underground. You want the first one of those.

t_hit = t[y < 0][0]

Prints 1.44. The exact answer from \(t = \sqrt{2h/g}\) is 1.43 s. Close, and our stepped answer is a hair late, which makes sense: the simulation always uses the speed from the start of each step, so it’s always a little slower than the real ball.

D2. The full parameter sweep, start to finish: the solar panel from HW 2 at noon on the equinox, one function run across ten tilt angles, results written to a file, and the file read back to find the winner. Fill in the two blanks.

The function already works on a whole array, so the first blank doesn’t need a loop. For the second: which row has the biggest number in the power column? data[:, 1] is the power column, and .argmax() gives the index of its biggest entry.

powers = panel_power(tilts)
...

Plots (week 6) · A2

PL1. Two panel brands, tested side by side. Run it, and before reading anything else, answer for yourself: how much better is BrightCell? Then list everything about this plot that pushes you toward that answer, and fix it.

Look at where the y-axis starts. What would the bars look like if it started at zero? And is there anything missing that would tell you what the numbers even are?

The plot makes BrightCell’s bar look about six times taller. The real difference is half a percentage point: 20.6 vs. 20.1, so BrightCell makes about 2.5% more power. That’s real, but it’s not a crushing.

What’s doing the misleading: the truncated axis (ylim(20.0, 20.7)), the editorial title, and no y-axis label or units at all. One honest version:

plt.bar(brands, efficiency, color="gray")
plt.ylim(0, 25)
plt.ylabel("Conversion efficiency (%)")
plt.title("BrightCell is about 0.5 points more efficient")
plt.show()

Starting at zero is the rule for bar charts, because the bar’s length is the thing your eye compares. (For dots or lines, zooming in can be perfectly honest, as long as the axis is labeled and the reader can see you zoomed. That’s the judgment part of A2.) And if half a percent really matters for your design, say that in words, rather than letting the axis say something bigger.

PL2. Make an honest plot of D2’s sweep. Fill in the labels, and run it.

Someone reading this plot cold needs to know what each axis is and in what units. Look at the docstring in D2 for both.

plt.xlabel("Panel tilt from horizontal (degrees)")

PD1. Some made-up summer highs for two years (made up, so don’t draw climate conclusions from them!). Fill in the two blanks: the average high for each year, and the number of months with a high above 29 °C.

“For each year” is the phrase that means groupby. For the second one: filter first, df[df["high_C"] > 29], then count the rows of what’s left with len(...).

  • 210.5263157894737, watts per square meter of panel. Sanity check: full sunlight delivers roughly 1000 W/m², so this panel turns about 21% of it into electricity. That’s a realistic number for a modern panel, so the dictionary is probably not lying to us.

DI2. Here’s a (shortened) reply from an hourly weather forecast API. It’s a dictionary, with dictionaries inside, with lists inside those. Fill in the blanks.

DI3. Looping over a dictionary hands you its keys, one at a time. Predict the output (roughly), then add titanium (4500 kg/m³) to the dictionary and run it again.

On the first pass material is "steel", so density[material] is density["steel"]. Then 7850 × 0.002 is…

Steel 15.7 kg, aluminum 5.4 kg, wood 1.2 kg. To add titanium, put "titanium": 4500 in the curly braces (or write density["titanium"] = 4500 before the loop, like in DI1). It comes out at 9.0 kg.

Sanity check: 2 liters of water is 2 kg. Wood is lighter than that (it floats!), and steel is about 8× heavier, which is about right if you’ve ever picked up a dumbbell.

You probably saw steel print as 15.700000000000001. That’s not a bug in our code. Computers store decimals in binary, and some decimals (like 0.002) can’t be stored exactly, so a tiny bit of fuzz shows up way out at the end. It’s harmless here. Use round(mass, 2) if it bugs you.

DI4. A logger collected four replies from the ISS API. One request failed, and one came back with a key missing. Predict everything that prints, including the final list.

Go one reply at a time. Does this reply have a "latitude" key? If not, the append line fails, and Python jumps to except without running the print("ok").

ok
skipped: KeyError('latitude')
ok
skipped: KeyError('latitude')
[51.45, 50.98]

Four replies in, two latitudes out, and the loop survived both failures. Something to chew on: suppose we were also collecting timestamp in its own list. The last reply has a timestamp. If we appended it before trying the latitude, the two lists would end up different lengths… and they’d no longer be parallel.

DI5. A reply from the ISS API (trimmed down a bit). We want the speed in meters per second. Before running anything, estimate it: the ISS goes once around the Earth in about 90 minutes, and once around the Earth is about 40,000 km. Then run the code. Do you believe it?

The estimate: 40,000,000 m in 90 × 60 = 5400 s. Compare that with what printed. Then think about the conversion out loud: 1000 m in a km, sure. But are there more seconds than hours in a given stretch of time, or fewer? So should a speed per second be a bigger number than the speed per hour, or a smaller one?

The estimate is \(40{,}000{,}000 / 5400 \approx 7400\) m/s. The code prints about 99,347,040,000 m/s, which is roughly 300 times the speed of light. Hmm.

The fix is to divide by 3600: there are 3600 seconds in an hour, so the ship covers 1/3600 as much ground per second as per hour.

v_ms = v_kmh * 1000 / 3600

Now it prints 7666 m/s, close to our 7400 (the ISS orbits about 400 km above the ground, so its circle is a bit bigger than the Earth’s, and a bit faster than our estimate). A ten-second estimate caught a mistake in a line of code that looks completely reasonable.

(rows, columns, channels). Every pixel has three numbers: red, green, blue. The last line asks for a single pixel: which row, which column, and how many numbers come back?

Three ways to be wrong (week 10) · S3

From Lights Out: a model can mislead us in three ways, and each comes with its own check.

  • Numerical: the model is fine, but we computed it badly (too big a step). Check: halve the step and see if the answer changes.
  • Physical: the model leaves out an effect that matters here. Check: compare with a measurement; ask what’s missing.
  • Extrapolation: the model worked where we tested it, but we’re using it somewhere else. Check: know the range you tested.

SIM2 above was the dramatic numerical failure (frozen coffee). Here’s the subtle one.

TW1. The coffee model from SIM1, run for 10 minutes with five different step sizes. Predict: as dt shrinks, does the answer go up or down? Does it keep changing forever? Then run it, and decide which dt is “small enough.”

Each step uses the cooling rate from the start of the step, when the coffee is hottest and cooling fastest. So does a big step cool the coffee too much, or too little?

5 37.5
2 42.94
1 44.41
0.5 45.09
0.25 45.43

Big steps cool too much, because each step holds the fastest cooling rate for the whole step. As dt shrinks, the answer climbs, and it settles: going from 1 to 0.5 changes it by 0.68 °C, and 0.5 to 0.25 changes it by 0.34 °C. Each halving changes it by about half as much as the last one. (It’s heading toward about 45.75 °C, which you can get with calculus. Not required!)

So which is “small enough”? It depends on the question, which is the honest answer and not a dodge. For “is my coffee still drinkable,” dt = 1 (within about 1.3 °C) is plenty. For a lab comparison with a thermometer good to 0.1 °C, we’d want to keep halving. What’s not OK is never checking: dt = 5 gives a perfectly plausible-looking 37.5 that’s 8 °C off.

The next two are on paper, checkpoint-style. For each: which kind of wrong, what’s the evidence, and what check would have caught it.

TW2. Our week 5 falling-ball simulation (no drag) matched a phone dropped from 2 m to within a few centimeters. A friend uses the same code for a skydiver jumping from 3000 m, and reports that they’d hit the ground at about 243 m/s.

NoteClick for the answer

Mostly physical: the model leaves out air drag. At 2 m the phone only reaches about 6 m/s, slow enough that drag barely matters, so the test passed. A skydiver goes fast enough that drag ends up balancing gravity, and real skydivers top out around 55 m/s (about 120 mph), which is a long way from 243.

Evidence: 243 m/s is roughly 540 mph, about the cruising speed of an airliner… for a person, falling belly-down. Estimation catches it. The check: compare against a measurement or a known number (skydiving terminal velocity is easy to look up), and ask “what did we leave out, and does it matter here?”

You could also call this extrapolation: we tested at 2 m and used it at 3000 m. That’s a fine answer with that evidence. The two overlap here, because the reason the model breaks far from where we tested it is a missing effect. The skill isn’t finding the one true label. It’s naming a failure mode and backing it up.

TW3. An electric car owner built a range model, miles = 3.5 × kWh in the battery, and checked it on 40 trips last summer and fall, at 40–90 °F. It was within 5% every time. Now they’re planning a 250-mile drive in January at −10 °F. The battery holds 75 kWh, so the model says 262 miles: “made it, with a little to spare.”

NoteClick for the answer

Extrapolation. The model was tested at 40–90 °F and is being used at −10 °F, well outside that range. Nothing in the model’s output warns you: it happily says 262, the same way it would in July.

Why it might fail out there: batteries deliver less when they’re cold, and the car is now using battery energy to heat the cabin, which it didn’t need to do in summer. (That second one is also a missing effect, so “physical” is a defensible label too.) Cold-weather range for electric cars can drop by a quarter or more.

The check: know the range you tested, and say it out loud along with the prediction (“this model is good for 40–90 °F”). Then either get data from a few cold trips, or plan with a big margin. A 5% cushion is not a big margin when you’re 50 °F outside your tested range.
