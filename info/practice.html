Tracing (weeks 2–3)

T1. Predict all three printed values on paper, then run to check.

Line by line, keeping a two-column table of a and b. Remember: = means is assigned — line 3 uses the values as they are at that moment, and b never updates afterward.

10, 4, 6. After line 1: a=6. Line 2: b=4. Line 3: a = 6+4 = 10 (b stays 4 — it stored a value, not a relationship).

T2. This one prints a single value. Commit to it before running.

The same line twice is not the same result twice — the second one starts from where the first one left off.

16. First squaring: 4. Second squaring squares the new value: 16. If you said 8, you read line 3 as “times the original x.”

Functions (week 3)

F1. Fill in the blank so the function matches its docstring, then verify with the test call — it should print 78.5 (approximately).

Area is π r² — and remember Python needs the power written explicitly. Two ways to write “r squared” both work.

return 3.14159 * r ** 2      # or: 3.14159 * r * r

The verification habit in miniature: 3.14 × 25 ≈ 78.5, hand-checkable before you trust it anywhere.

F2. Predict what prints — this is the local-names idea from the week 3 reading, wearing a different shirt.

The n inside the function is the function’s private n. What happens in the function stays in the function — only the return value escapes.

1 then 11. The outer n is untouched; add_ten worked on its own local copy and shipped the result out through return.

Logic (week 4)

L1. Four calls, four predictions on paper, then run.

Top to bottom, first true branch wins. And check the boundaries with a jeweler’s eye: is 100 greater than 100?

highway, highway (100 is not > 100 — the boundary lesson), too fast, city (−5 falls through to else — is that what a spec would want? That question is week 4’s whole point).

Loops (week 5)

X1. Fix the loop so it prints the sum of the squares of 1 through 4 (which is 30 — verify that by hand first).

Run it as-is and look at what you get (16). The loop isn’t accumulating — each pass throws away the previous total. What’s missing from the right-hand side?

total = total + k * k

The accumulator pattern: the new total is built from the old total. total = k * k just overwrites, and you end up with only the last pass (16).

X2. Assembly problem: these lines compute the average of a list, but they’re scrambled. Reorder them (cut and paste in the editor) so it runs and prints 5.0.

Three constraints: names must exist before they’re used; the indented line belongs to the for; the print needs everything finished. (Also — could you avoid hard-coding count = 3? Python’s len(values) exists. Not required, but that’s the better program.)

values = [3, 5, 7]
total = 0
count = 3
for v in values:
    total = total + v
print(total / count)

The first three lines can go in any order among themselves — data dependency, not ceremony, dictates sequence. That observation is the entire point of assembly problems.

Arrays (weeks 5–6)

A1. One line replaces the whole loop: fill in the blank so t holds the fall time for every height at once, then print it.

The formula is \(t=\sqrt{2h/g}\), and NumPy’s square root is np.sqrt(...). Write the arithmetic as if h were a single number — the array handles the “for every value” part itself.

t = np.sqrt(2 * h / 9.81)

Sanity anchor: the first entry should be ≈ 0.45 s and each height is 4× the previous, so each time should be 2× the previous (√4 = 2). Check the printout against that — a free verification pattern hiding in the problem’s structure.
