Data in, data out — and honest plots

Week 6 — read before Tuesday

Every number we’ve computed with so far, we typed into the program. The 24 hours of wind speed, the balloon’s \(k/m\), even the “sensor glitch” at −999 was manually typed-in. Real data doesn’t arrive that way. It arrives as a file — from a sensor, a colleague, a government agency — and it’s usually far too long to type.

This week we’re going to learn how to get numbers out of a program and into a file, and then how to get numbers from a file into a program. We’ll also talk about plotting, which we’ve been doing informally for a couple weeks but will be more detailed about now. Notably, we’ll talk about what good, honest plots look like, and how the default settings in our programming languages don’t really get us there. (And LLMs still do a bad job creating plots, in my opinion!)

Writing a file

Let’s start with results we already have. Here’s the design-speed sweep from week 4’s activity: eleven blade designs, one day’s energy for each. We’ll compute it exactly as before, and then add one line at the end.

This might not look very different from what we’ve been doing, but there is something extra happening in the background. I guess pyodide, the tool that is running code on this website, is saving a temporary file called “design_sweep.csv”, and then openining it and displaying the results. In Colab it is clearer that a file is created, and you can download it.

Within the np.savetxt function call:

  • "design_sweep.csv" is the file’s name. It is common to save arrays in a “comma-separated values” (csv) format.
  • np.column_stack([design_speeds, totals]) puts two parallel arrays together side by side as two columns. One row holds, for example, design_speeds[4] and totals[4].
  • delimiter="," puts a comma between the values in a row.
  • header="..." writes a first line naming the columns. This is your chance to give some details about the file contents — e.g., it might be a good idea to put the units in the names. A column called energy would leave the next reader guessing whether it’s kWh, MWh, or joules.
  • comments="" — see the margin.
  • fmt="%.1f" says “write each number with one digit after the decimal point.”

By default, savetxt puts # in front of the header line, marking it as a comment. NumPy is happy with that. Most other programs (Excel, pandas next week) are not, and they’ll think the first column is named # v_best_m_per_s. Setting comments="" turns that off.

Then print(open(...).read()) allows us to see the file on this webpage. In Colab you can just double-click the file to look at it (more on where it lives in a moment).

Where did the file go?

A file lives in a folder, and its full address is called its path. Something like /content/design_sweep.csv means “the file design_sweep.csv inside the folder content.” When we wrote just "design_sweep.csv" with no folder, Python put it in whatever folder it was currently working in.

In Colab, that folder is /content: if you want to see what is in it, click the folder icon in the left sidebar. design_sweep.csv will be there after you run the code. Double-click it to see the contents.

ImportantColab’s files are temporary

The files in Colab’s panel exist for a short while — Google will remove them and reclaim the space if you go idle for a while or close the notebook. If you want to keep a file, hover over it, click the three dots, and Download.

The reverse also works: to use a file you have, drag it onto that Files panel, or use the upload button at the top of the panel. It then is in /content and you can refer to it by name. It will also vanish when the session ends, so you’ll need to upload it again next time.

There’s a more permanent option: connecting Colab to your Google Drive, so files live in Drive instead.

Reading it back

Now the other direction. np.loadtxt reads a CSV of numbers into an array:

Two new things here. First, skiprows=1 tells loadtxt to skip the header line, because “v_best_m_per_s” is not a number, and loadtxt only reads numbers.

Second, data is a two-dimensional array — a grid, 11 rows by 2 columns, which is what data.shape reports. To get one value out of a grid we need two indices, row then column: data[4, 1] is row 4, column 1, which is the energy for the 10 m/s design. The colon means “all of them,” so data[:, 0] reads as “every row, column 0” — the whole design-speed column.

We are still counting from zero! Column 0 is the first column. Row 0 is the first row of numbers, since the header was skipped.

In practice we usually pull the columns apart right away and give them variable names, which gets us right back to the parallel arrays we know:

v_best = data[:, 0]
energy = data[:, 1]
print(v_best[energy.argmax()])

With this data now part of our program, we can do any sort of calculation we need to. Calculate the average, the max, the sum, etc.

Caution

Try deleting skiprows=1 from the cell above… you’ll get an error message.

Tip

Check out the file before computing anything: What are the columns, what are the units, does anything look strange?

loadtxt only reads numbers. A file with words or dates in it (a column like 2026-09-10, say) will cause problems.

Plotting data

We’ve plotted some functions, e.g. \(C_p(v)\) and the falling ball. Plotting data works the same way, but might involve a couple different choices. Here are some Boulder temperatures, including a bad reading:

When we plot the data, the bad reading is obvious: it is the extreme outlier. A plot is a verification tool that looks at every row at once! So: plot the raw data before you process it.

A few standard choices when we plot data:

  • Markers, not lines, for measurements. "o" draws a dot at each data point with nothing in between. Our data collection is discrete, and so the representation of the data should be as well. (Theoretical equations or modeling equations can be solid lines because they are continuous.)
  • Labels with units. In many fields it is standard to report units you would not expect. For example, refrigerators are often measured in BTUs instead of the SI unit J. Don’t assume SI units — report the units in your plot!
  • A legend when there’s more than one thing. label= on each plot call, then plt.legend(). Or, if possible, add annotation arrows and label the data directly.

A plot can be an output file too. plt.savefig("boulder_sept.png", dpi=200), placed before plt.show(), writes the figure to Colab’s Files panel. You can download it and put it in a report.

Honest plots

Here are the same six data points plotted twice: a motor’s efficiency, measured monthly.

On the left, the y-axis spans 0 to 100%, and the story is basically flat: a stable motor drifting up by half a percent. On the right, the axis spans 94.0 to 94.9%, the line is thick and red, the title sets misleading expectations, and the units have disappeared. The claimed story is that there has been a dramatic improvement. Neither plot contains a false number. I think the second one is still untruthful!

Caution

Try it: change the honest plot’s set_ylim(0, 100) to set_ylim(90, 100), then (94, 95).

Axis truncation is one way to make a misleading plot. Some other ways: a cherry-picked range (start the x-axis right after the bad quarter), missing units, two y-axes scaled to make unrelated things look correlated, 3D bars whose volumes exaggerate the differences.

As engineers, we should strive to produce plots that tell an accurate story. That includes being honest about bad data and uncertainty! We’ll also be on the receiving end of misleading plots and need to understand what the true story is so we can make good decisions.

TipThink

Is a truncated axis always dishonest? A half-percent drift might actually matter — maybe it is something wearing-in and we are monitoring to make sure it is following the typical pattern. In such a case, it may be a good (honest) idea to say what is happening: “note: y-axis spans 94–95% to show the drift over one month of use.”

In-class work

Last Thursday you ran the drag simulation for four objects and recorded the results down by hand. Let’s do it properly this time: many objects, write the results to a file, and then hand the file to someone else.

CautionInstructions

Grab your drop function from last Thursday then try each of these in Colab.

  1. Sweep it. Run your drop function from a height of 10 m for 26 values of k_over_m, from 0 to 5: np.linspace(0, 5, 26). For each one, record the fall time and the impact speed in pre-allocated arrays.
  2. Write it. Save all three arrays to drag_sweep.csv with a header that names each column and its units. Double-click the file in Colab’s Files panel and check that it’s what you meant to write.
  3. Trade it. Download your file and send it to the person next to you (email, AirDrop, whatever works). Upload theirs into your Colab.
  4. Read theirs. Load it and plot fall time against \(k/m\), with markers, labels, and units. Mark roughly where the balloon, the phone, and the steel ball sit on the curve.
  5. Talk about the handoff. Could you use your neighbor’s file without asking them anything? If you had to ask something (which column is which? are those speeds negative?), that question is a gap in their header. Fix yours.

The steel ball and the phone will be scrunched up against the left edge. That’s not a mistake — their \(k/m\) is tiny compared to the balloon’s. Whether that plot needs a different x-axis to be useful is a fair question… or you could replace plt.plot(...) with plt.semilogx(...).
