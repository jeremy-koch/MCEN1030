A loop that remembers — simulating a falling ball

Week 5, Lesson A — read before Tuesday

Last week we used for loops to compare designs: five rotor diameters, and eleven blade designs, one per v_best value. The order didn’t matter: we could have swept the diameters backwards, or shuffled them, and every answer would have come out the same. The passes through the loop were independent.

This week we add one wrinkle: what if each pass needs to know what the last pass worked out? Last week: the loop evaluated a formula many times; today: the loop builds an answer that has no formula. If you’ve ever heard someone say the computer is simulating a result, this is it!

Think First

Recall

  1. Last Thursday: in totals[i] = turbine_power(good, diameters[i]).sum(), could you have run the five passes in any order? Would the answers change?
  2. Also last Thursday: the bring-to-class had you trace total = total + x inside a loop. Did that loop’s passes depend on each other?

Look Ahead

  1. If you know where a ball is right now, and how fast it’s falling right now, could you guess where it’ll be a tenth of a second from now? How wrong would that guess be?
  2. Our ball is going to fall. What in the code is going to tell it that the ground exists?

For this example, the order doesn’t actually matter — addition doesn’t care about order — but the spirit was there: we were working with an accumulator where we built-up a value step-by-step using a for loop.

In this reading we’re going to accumulate something more interesting than a running total.

A loop variable that carries information from one pass to the next is often called a state. It’s the program’s memory of where it has gotten to.

A rule instead of a formula

In several places on this webpage, we’ve been using

\[ t = \sqrt{\frac{2h}{g}} \]

to describe how long a dropped object takes to fall. That is a “formula”, but it is very idealized, notably neglecting drag. Many times in engineering, we don’t have an explicit formula that connects an input to an output, but we do have a rule that we can use computationally to get an approximation of the connection.

Let’s keep thinking about the drop time, and we will build up to something more complex by Thursday. Suppose I tell you a ball is 10 m high and, at that moment, falling at 3 m/s. If we measure \(y\) upward from the ground, then falling means \(v = -3\) m/s. Where is it one tenth of a second from now? You might note

\[ \Delta y = (-3\text{ m/s})(0.1\text{ s}) = -0.3\text{ m} \]

— three tenths of a meter lower than it started — and that would be pretty close, although the ball does speed up during that interval (because gravity manifests as an acceleration). We could write these rules generally as

\[ \begin{align*} y_{\text{new}} &= y + v\,\Delta t \\ v_{\text{new}} &= v + a\,\Delta t \end{align*} \]

The first of these equations says: your new position is your old position plus however far you traveled. The second says the same thing about speed: your new velocity is your old velocity plus however much gravity changed it. If we wanted to predict how far you’ve moved, we could calculate these two things over and over again, keeping track of the position \(y\) and velocity \(v\) after every “time step” \(\Delta t\). Do it a few hundred times and you can trace the trajectory of a falling object.

Important

Notice the speed changes each time we do the calculation, and so the displacement \(y_\text{new}-y\) will change as well (assuming the same \(\Delta t\)).

Tip

Pay attention to signs! If \(y\) is measured upward from the ground, and then the object falls with gravity, the acceleration \(a = -9.81\) m/s² is negative! The velocity \(v\) will also be negative. More important than memorizing conventions is paying attention to the physics and making sure it matches with your intuition.

Keeping track

Those two rules are each an accumulator: y = y + something, v = v + something — same idea as total = total + x. The only difference is that now there are two of them and they rely on each other.

With this scheme, the first time step forward leaves us at the original value of \(y\). This isn’t a bug — our initial value of \(v\) is zero, and in this discrete approximation of real physical behavior, that causes \(y\) to be the same in its first two values.

A few notes:

There are n_steps + 1 slots for n_steps steps. Taking 30 steps means starting in one state, then moving to 30 new states. Off-by-one errors are common!

Element zero is the initial condition. y[0] = 10.0 is not a calculation, it’s an input: we say that it starts at a height of 10.

The loop reads i and writes i+1. This can’t be done with a NumPy array operation, no matter how clever. y[i+1] needs v[i], which needed v[i-1]… all the way back to the beginning. NumPy can do a million multiplications at once because none are dependent on each other. Here, the dominoes have to fall in order.

Does this match expectation? The speed should increase with time, as gravity causes an acceleration. This will manifest as a curve that starts flat and then steepens.

What might be unexpected: the object punches through \(y=0\) and ends up thirty-two meters underground.

ImportantThe model knows only what you told it

Nowhere in that loop did we mention that the ground exists, or that balls stop at it. We told the program one thing — gravity pulls down.

A simulation is a small set of rules we chose… the computer does exactly what we tell it to do. If we don’t tell it about the ground, it doesn’t do anything about the ground!

Is any of this right?

A verification question! We have been assuming no air resistance — in such a case there is a formula we can check against:

\[y = h_0 - \tfrac{1}{2} g t^2\]

At \(t = 1.0\) s from 10 m, that’s \(10 - 0.5(9.81)(1) = 5.095\) m. Let’s see what our stepper says, at a few different step sizes.

Two things to note:

Smaller steps, smaller error. At dt = 0.5 we’re off by 2.45 m, terrible; at dt = 0.01 we’re off by 5 cm. The price for taking smaller steps is taking more steps, but the computer doesn’t mind.

But the velocity is exactly right at every step size. The velocity comes out to \(-9.810\) in every row… gravity is constant, so v = v - g*dt isn’t an approximation at all; it’s exact. Velocity is not constant during a step, though, and y = y + v*dt pretends it is: we use the speed from the start of the step for the whole step, so we under-count the distance fallen and our ball sits a little too high.

So this new method works, but why bother when the formula is exact and easier to program? Because the formula only exists for the idealized problem. The equation \(y = h_0 - \frac12 g t^2\) is true because the acceleration is constant — if the acceleration depends on anything, the simple formula is no longer applicable. But… the loop method doesn’t even notice! Just tell your code the new value for a and it is ready to go!

Why would it change? Most notably: air resistance — air pushes back harder the faster you go, so the acceleration depends on the velocity… but the velocity depends on the acceleration… which depends on the velocity. For our time-stepper it’s one extra line, inside the body we already wrote.

When does it land? Masking keeps only the entries where a condition is true:

above = y > 0          # True wherever the ball is above the ground

The last of those times is (just about) when it landed. How do you get the last element of an array?

Challenge

Which angle throws the ball farthest?

Now throw the ball forward and up, at an angle \(\theta\) above the ground. The ball moves in two directions at once, so it needs a position and a velocity in each: \(x\) and \(y\), \(v_x\) and \(v_y\). The rules are the same ones as before, written out once for each direction:

\[ \begin{align*} x_{\text{new}} &= x + v_x\,\Delta t & y_{\text{new}} &= y + v_y\,\Delta t \\ v_{x,\text{new}} &= v_x + a_x\,\Delta t & v_{y,\text{new}} &= v_y + a_y\,\Delta t \end{align*} \]

Vertically nothing has changed: \(a_y = -g\). If we are ignoring drag, there is no acceleration in the \(x\)-direction: \(a_x=0\).

Throwing at speed \(v_0\) and angle \(\theta\) splits the throw into a sideways part and an upward part:

\[ v_{x} = v_0 \cos\theta, \qquad v_{y} = v_0 \sin\theta \qquad \text{(at the start)} \]

As in HW 2, NumPy’s cos and sin want radians. np.radians converts degree measurements to radians, or you can start thinking in radians!

  1. Build it. Throw from the ground at 10 m/s and 30°. Plot the path of the ball — y against x. Where does it land?

  2. Check it against physics. A 30° throw and a 60° throw should land in the same place (assuming no drag). Do yours? How close is “the same”?

  3. Sweep it. Put your throw inside a function, landing_distance(angle), that returns where the ball lands. Then run it for every angle from 5° to 85°, keep the answers in a pre-allocated array, and use argmax to find the best angle. Plot distance against angle.

  4. Question the famous answer. Everything so far launched from the ground. Launch from hand height, 1.5 m — then from the top of a 10 m building. Does the best angle stay the same?

A loop inside a loop is called a nested loop. The inner one always runs to completion before the outer one takes its next step.
