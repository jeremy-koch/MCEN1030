Fetch: APIs and JSON

Week 8 — read before Tuesday

This week we are going to “fetch” data ourselves, instead of having a dataset given to us. Our first reading included the line:

From a few lines of code you can pull the live position of the International Space Station…

We’ll know how to do this after today. We’ll learn what an API is, what the response looks like when it comes back (“JSON”, and Python reads it as a dictionary), and what to do when you don’t get a response.

Think First

Recall

  1. Week 7: pandas let us grab a column by name (df["temp_C"]) instead of by position (AL2). Why was that such an improvement?
  2. Week 6: before trusting any data file, what do you check?

Look Ahead

  1. When the weather app on your phone shows today’s temperature, where does that number actually come from?
  2. Suppose your program asks a server for data every 30 seconds for 20 minutes, and at minute 7 the Wi-Fi hiccups. What should your program do?

What an API is

An API (application programming interface) is, for our purposes, a web address that returns data instead of a web page. You send a question to a URL, and a computer somewhere sends back an answer.

Here’s one that gives the live position of the International Space Station. Click it on whatever device you’re reading this on:

https://api.wheretheiss.at/v1/satellites/25544

Refresh the page a few times and watch the numbers change… it’s moving fast!

That’s interesting, but we are probably more interested in using the answer. In Python:

import requests
r = requests.get("https://api.wheretheiss.at/v1/satellites/25544")
info = r.json()
print(info)

requests.get sends the request for information and .json() turns the reply into something Python can work with.

The code cells on this page run inside your browser, which isn’t set up for requests — so run in Colab. The cells below use a reply I saved earlier.

JSON, and the dictionary

Here’s what came back when I clicked that link on October 10 (lightly rearranged so it fits on the page):

{"name": "iss", "id": 25544,
 "latitude": 51.452776061797, "longitude": -116.29532419749,
 "altitude": 430.56388078893, "velocity": 27565.817344208,
 "visibility": "daylight", "timestamp": 1791654325,
 "units": "kilometers", ...}

This is JSON (“JavaScript Object Notation”, not only used with JavaScript), the format most APIs speak. Base Python has a dictionary that has a structure that looks like: "key": value. The above is a dictionary, and for example, name is a key, and iss is the associated value.

Dictionaries function similarly to a DataFrame in that we reference things by name, not by position:

Latitude 51.45° N, longitude 116.30° W. Paste 51.45, -116.30 into a map and the ISS was over the Canadian Rockies.

Now, is 27,566 a believable speed? The API says "units": "kilometers", so this is presumably km/h. Let’s check it against something we know: the ISS goes around the Earth about every 90 minutes. Its orbit is a circle of radius \(6371 + 431 \approx 6800\) km, so one lap is \(2\pi \times 6800 \approx 42{,}700\) km. At 27,566 km/h, that takes \(42{,}700 / 27{,}566 \approx 1.55\) hours, or about 93 minutes.

Never guess a key

What happens if we ask for a key that isn’t there? Try adding info["lat"] to the above cell. You should get KeyError: 'lat'.

Python won’t guess what you meant: the key has to match exactly, capitals and all. A good strategy: print the whole reply once, find the thing you want, and then write the path to it. Look first, then extract.

Nesting: dictionaries inside dictionaries

The ISS reply is simple: one level of keys. Most APIs aren’t. Here’s what a free weather service (Open-Meteo) sent back when I asked for the current conditions in Boulder:

weather["current"] is itself a dictionary, so we can index into it again: weather["current"]["temperature_2m"]. Read the path left to right, like directions: go to "current", then inside that go to "temperature_2m".

This reply also has something nice in it: the units travel with the data ("current_units"). Wind in km/h, not m/s or mph. And look at the time… 17:45 in "GMT". That’s not Boulder time. It was 11:45 in the morning here.

When the question doesn’t get answered

So far, every request worked. However: servers go down, Wi-Fi drops, free APIs get busy and tell you to slow down, and sometimes we just make a typo in the URL. Let’s see what failure actually looks like. Here’s the reply when I asked for a satellite number that doesn’t exist:

{"error": "satellite not found", "status": 404}

The server answered, but not with what we wanted: we got a JSON/dictionary with just two keys, "error" and "status". So if the next step in our code looks at info["latitude"] we’ll get a KeyError, and the program stops. If the Wi-Fi is down entirely, it’s worse: requests.get itself fails with a ConnectionError and never gets as far as a reply.

For one request in a notebook, a crash is fine: sigh and run the cell again. But maybe we’ve built a data logger that does an API request every 30 seconds for 20 minutes, and maybe we run it and step out for coffee. If there is a hiccup at minute 7, you’ll come back to a program that stopped 13 minutes ago. What we’d really like is for the program to say “that one didn’t work, skip it” and carry on.

That’s what try and except are for:

Python tries the indented block under try. If everything in it works, the except part is ignored. If anything in it fails, Python doesn’t crash. It jumps straight to the except block, runs that instead, and carries on with whatever comes next. err holds the error, so we can still see what went wrong.

In real fetching code, the try block would hold the request itself:

try:
    r = requests.get("https://api.wheretheiss.at/v1/satellites/25544", timeout=10)
    info = r.json()
    lat = info["latitude"]
except Exception as err:
    print("Skipped one reading:", repr(err))

(timeout=10 means “if there’s no answer in 10 seconds, give up.” Without it, a stuck request can wait a longggg time.)

Caution

try/except is powerful, and that makes it a little dangerous. It catches every error, including the ones that are your fault. Misspell a key inside a try, and the program will “skip” every reading without complaining. So keep the try block small (just where you need it), always print what was skipped, and count the skips at the end. Twenty requests with two skips is a hiccup, twenty requests with twenty skips is a bug.

There’s a third word in this family, raise, which lets your own code create an error on purpose: “this temperature is negative in kelvin, stop everything.” Useful when you write tools for other people to use.

Bring to class

  1. Navigate. Using the weather dictionary above, write the line of Python that gives the current wind speed. What does weather["current_units"]["temperature_2m"] give you? What does weather["temperature_2m"] give you, and why?
  2. Predict. The ISS is moving at about 27,600 km/h. How far does it travel in 5 minutes? The Earth is about 40,000 km around the equator. If the ISS were flying due east along the equator, how many degrees of longitude would it cover in those 5 minutes?

In class we’ll fetch the real thing and check your prediction against it.

In-class work

We’ll ask the ISS where it is a bunch of times, build a small dataset out of the answers, and use it to check the ISS’s speed a second way. Then we’ll point everything we learned at an API we’ve never seen.

  1. One request. Fetch the ISS’s position with the three lines from the reading and print the whole reply. Pull out the latitude, longitude, altitude, and velocity. Where is it right now? Paste the coordinates into a map. Redo the 93-minute check with the altitude and velocity you got.

  2. What time is it? The timestamp is a big number like 1791654325. That’s Unix time: the number of seconds since midnight UTC on January 1, 1970. (This is how most computers count time.) pd.to_datetime(info["timestamp"], unit="s") converts it. What time zone is it?

  3. Ask several times, but patiently. We want to ask 10 times, 30 seconds apart, and keep the latitude, longitude, and time of each answer. The skeleton is below, with everything inside the loop removed except the waiting.

    import time
import requests
import pandas as pd

url = "https://api.wheretheiss.at/v1/satellites/25544"
track = {"timestamp": [], "latitude": [], "longitude": []}

for k in range(10):

    # your code here

    time.sleep(30)          # wait 30 seconds before asking again

df = pd.DataFrame(track)

    Before you write anything, talk with your partner: what is track? (Look at its curly braces.) Then write the body. Each pass through the loop should ask for the position, pull out the three values, add them to the three lists in track, and print the loop number k with either “ok” or the reason it was skipped. Think about what a skipped request should do, and where the try and except belong. One design question to settle before you run it: should you pull out all three values before appending any of them, or append each as you go? (What would happen to the three lists if "latitude" were missing from one reply?) When it’s working, it takes about 5 minutes, so keep the next step in mind while it runs.

    While it runs, talk about time.sleep(30). This API allows about one request per second, and if it is busy it might allow even fewer. If a whole classroom did that in a loop it starts to look like an attack — we might get blocked!

  4. Check your prediction. Look at df. How many degrees of longitude did the ISS cover in those ~5 minutes (first row to last)? (If you get something huge or negative, the track crossed the date line.) Compare with your bring-to-class prediction. They probably don’t match exactly. Can you think of why? (Hint: does the ISS actually fly along the equator? And what is the Earth doing underneath it?)

  5. How fast did it go? Now we have positions and times, so we can measure the speed ourselves instead of reading it off the reply. Take the first row and last row of df. Between two nearby points on a sphere of radius \(R\), the distance traveled is

    \[d = R\,\sqrt{(\Delta\varphi)^2 + (\cos\bar\varphi \cdot \Delta\lambda)^2}, \qquad v = \frac{d}{\Delta t}\]

    where \(\varphi\) is latitude, \(\lambda\) is longitude, \(\Delta\) means (last − first), and \(\bar\varphi\) is the average of the two latitudes. The first term under the root is the north–south distance. The second is the east–west distance, with the \(\cos\bar\varphi\) there because a degree of longitude gets shorter as we move away from the equator. Both angles have to be in radians (after import numpy as np, np.radians converts and np.cos takes radians). Use \(R = 6371 + \text{altitude}\) in km, with the altitude from step 1, and get \(\Delta t\) in hours from the timestamps (which are in seconds). Compute \(v\) and compare it with the velocity from the API. Do they agree? If they’re off by a little, in which direction, and why?

  6. Break it on purpose. Change the satellite number in url to 99999999, and run the loop for 3 requests (change range(10)). What does your program print? Look closely at which error it prints. Now take out the try/except (keep the code inside it) and run it again.

A different API

The ISS API is one example. Now let’s use a different one that you’ve never seen, and use what we learned: print the reply, look at it, then write the path.

The US Geological Survey publishes a list of every earthquake it has detected on Earth, updated every minute. Here’s the past hour:

https://earthquake.usgs.gov/earthquakes/feed/v1.0/summary/all_hour.geojson
  1. Look first. Fetch it. The whole reply is long, so don’t print all of it. Start with the keys at the top level (list(reply.keys())), then look at one piece. Where do the earthquakes live? What is each earthquake, and what’s the structure inside it?
  2. Find the biggest. How many earthquakes were there in the past hour? (There are two places you could find that out; do they agree?) Which one had the largest magnitude, and where was it? Write the path to its magnitude and its place.
  3. Where, and how deep? Each earthquake has "coordinates" with three numbers. Work out what they are, using the biggest earthquake’s place to check yourself. (Careful: this API doesn’t put them in the order the ISS one did!)
  4. How long ago? An earthquake’s time is in the same Unix time as the ISS timestamp, but not in the same units. Figure out the units by finding when the biggest earthquake happened, then compare it against the reply’s generated time (in metadata) to find how many minutes ago it was. Does your answer sound plausible for a feed of “the past hour”?
  5. Keep it going. Write a try/except loop that asks the USGS for the number of earthquakes in the past hour, five times, 10 seconds apart. (How often do you expect the answer to change? Is 10 seconds a sensible choice?)
