Reading code & the full cycle

Week 2, Lesson B — read before Thursday

Tuesday you ran code. Today you learn to read it — which, in a course where AI handles production, is the load-bearing skill — and then we put the whole week-1 philosophy through one complete lap: spec → prompt → annotate → verify.

Think First

Recall

  1. From Tuesday: what does = actually do, and why is count = count + 1 not nonsense?
  2. From week 1: what fills the gaps in an under-specified prompt?

Look Ahead

  1. Could you convince someone a program is correct without running it?
  2. What’s the difference between a comment that says what a line does and one that says why it’s there?

The reading vocabulary

You already know enough Python to read most short engineering scripts. Here’s the honest inventory, plus two constructs you haven’t formally learned but will see in AI output long before we cover them:

You see It means
x = 5 store 5 under the name x (“gets”, not “equals”)
print(x) display the value of x
x ** 2, x / y power, division
# text note for humans; Python skips it
if condition: preview (week 4): run the indented block only when the condition holds
for item in things: preview (week 5): run the indented block once per item

You don’t need to write if or for yet. You need to recognize their shape — indentation marks the “inside” — so AI-generated code doesn’t look like hieroglyphics for the next two weeks.

Tracing: running code in your head

To trace a program, be the computer: go top to bottom, one line at a time, keeping a little table of every variable’s current value.

(Runnable — after your trace. The print line is added so the machine can confirm your paper.)

NoteClick to see the trace

After line 1: a = 2. After line 2: a = 2, b = 5. After line 3: a = 20, b = 5 (note: b doesn’t move — it stored a value, not a relationship). After line 4: c = 25.

If you got c = 25, you can trace. If you got c = 7, you read = as algebra again — go re-run the week-2a mental patch.

Tracing is slow and that’s fine. It’s a verification instrument, not a way of life: you deploy it on the lines you don’t trust.

The annotation discipline

When an AI hands you code, you will annotate it: a comment on every line or logical block, in your own words, saying what it does and why it’s there. Two rules, permanent for the semester:

Important

Rule 1: A line you cannot annotate is a line you do not understand, and a line you do not understand does not enter your program. Investigate it or delete it.

Rule 2: Annotate the why, not just the what. # convert to liters beats # multiply by 1000 — the first survives a bug hunt, the second is just the code again, slower.

This feels tedious in week 2. It is also, quietly, your entire preparation for the final defense — a project annotated as it grows is a project you can explain under examination. Students who skip this discipline meet it again in week 14, at the worst possible time.

One full lap: the pool problem

The problem: How long will it take to fill a backyard swimming pool with a garden hose?

Step 1 — Specification. Before any AI is involved, decisions: Inputs — pool length, width, depth (m), hose flow rate (L/min). Output — fill time in hours, displayed with units. Assumptions — rectangular pool, constant flow, starts empty, no evaporation or splashing (fine at this timescale). Edge cases — zero or negative flow rate should stop with a clear error, not divide by zero or report a negative time.

Step 2 — The prompt. Notice how the spec practically is the prompt:

Write a short Python script that computes the time to fill a rectangular pool. Inputs as variables: length, width, depth in meters, and flow rate in liters per minute. Convert consistently, output the fill time in hours with a printed sentence including units. Comment each step.

Step 3 — Annotate what comes back. Suppose the AI returns:

The two arrow-comments are annotation doing its real job: flagging the hinges — the lines where a silent error would live.

Step 4 — Verify. Hand estimate: volume is \(8 \times 4 \times 1.5 = 48\) m³ = 48,000 L. At ~10 L/min that’s ~4,800 min ≈ 80 hours. Program says 84.2. Agreement — trust earned. Unit check: trace the units through each line (they cancel to hours — do it). Edge case: set flow = 0 and predict before running what happens.

About 3.5 days of continuous garden hose. Verification sometimes delivers engineering judgment for free: the answer is “rent a water truck.”

When the AI gets it plausibly wrong

Same prompt, different day, and the returned code contains:

volume_L = volume_m3 * 100    # convert cubic meters to liters

It runs. It plots nothing suspicious. It reports a fill time of 8.4 hours — brisk, believable, wrong by a factor of ten. The comment even asserts the conversion confidently. Only two things catch this: the hand estimate (80 ≠ 8.4) and the annotation pass (is 1 m³ really 100 L? A cube 10 dm on a side holds 10 × 10 × 10 = 1000 L). Nothing about running the program catches it. This is the “confident, invisibly wrong” failure mode from week 1, in the wild — and you just watched two cheap habits kill it.

Below is an AI-generated script with three planted flaws: one syntax error (won’t run), one logic error (runs, obviously wrong), and one silent error (runs, plausibly wrong). On paper: annotate every line, name all three flaws, and state what the correct fill time should be. Do not run it first — Thursday’s opening vote is which line hides the silent one, and the fun is finding it by reading.

flow = 9.5            # hose flow rate, liters per minute
length = 8            # m
width = 4             # m
depth = 1.5           # m

volume = length * width * width   # pool volume, m^3
volume_liters = volume * 1000     # convert m^3 to liters
minutes = volume_liters / flow    # minutes to fill
hours = minutes * 60              # convert minutes to hours
print("Fill time:", hours "hours")
