Pandas: 60,000 rows without fear

Week 7 — read before Tuesday

Week 1 promised that engineering datasets have 60,000 rows and that Excel is not going to help you. Today: the tool that will.

Think First

Recall

  1. Week 6: what are the F2 questions you ask of any data file before computing?
  2. What’s the largest spreadsheet you’ve personally scrolled through? How did that go?

Look Ahead

  1. “Find every row where temperature exceeded 80 °C” — how would you even start in Excel with 60,000 rows?
  2. If a program reduces 60,000 numbers to 5, how do you verify the 5?

When spreadsheets break

Excel is genuinely good at what it’s for: small tables, quick looks, hand-entered data, one-off arithmetic. But a test rig logging 10 sensors at 100 Hz produces 60,000 rows in a minute. At that scale Excel becomes a scrolling punishment: slow, click-driven, unrepeatable — and unrepeatable is the professional disqualifier. “I clicked some filters and sorted some stuff” is not a workflow anyone can rerun, audit, or apply to next week’s file. (A3 provenance again: an analysis nobody can rerun is a rumor with formatting.)

The DataFrame

Pandas gives you the DataFrame: a whole table living in one variable, columns addressed by name.

import pandas as pd
df = pd.read_csv("motor_test_log.csv")
df.head()          # show the first 5 rows — ALWAYS the first thing you run

head() is week 6’s “look before you compute” habit, industrialized: five rows tell you the column names, the units situation, and whether anything is obviously deranged, without printing 60,000 lines.

df["temp_C"]            # one column, by name
df["temp_C"].mean()     # one meaningful number from 60,000
df["temp_C"].max()
df.describe()           # summary statistics for every numeric column at once

Filter, summarize, reduce — the P3 verbs

Filtering is week 4’s booleans, applied to an entire column at once:

hot = df[df["temp_C"] > 80]      # a new DataFrame: only the too-hot rows
len(hot)                          # how many were there?
hot["rpm"].mean()                 # what was the motor doing during them?

Read the inner part first: df["temp_C"] > 80 produces 60,000 booleans; wrapping it in df[...] keeps the rows where it’s True. Grouping answers “broken down by…” questions:

df.groupby("test_phase")["temp_C"].mean()   # average temp in each phase of the test

That’s the whole P3 skill: an engineering question in English (“how hot did it run during startup vs. cruise?”) becomes a filter, a group, and a summary — 60,000 rows in, five meaningful numbers out, in three repeatable lines.

Tool choice is an engineering decision

So is Excel dead? No — and “which tool?” is itself a skill this course assesses. Quick look at a 30-row file a colleague sent? Excel, obviously; importing it into pandas would be ceremony. Repeatable analysis of instrument data? Pandas. The rule of thumb: Excel for looking, pandas for pipelines — if you’ll do it twice, or on data too big to eyeball, or anyone might ask “how did you get this?”, it’s a script.

AI, pandas, and the spot-check

Pandas is where AI assistance genuinely shines — “group by test phase and report the mean and max temperature of each” comes back correct and idiomatic almost every time. It is also where silent wrongness thrives, because the failure modes are invisible at scale: filtering > 80 when the spec meant >= 80, grabbing temp_F when you meant temp_C, a groupby that quietly dropped rows with missing values. The verification move is the spot-check: take the AI’s five-number answer, pick one group, and verify it against a handful of rows you can inspect by eye — or better, against a miniature of the dataset where you know every answer. Which is exactly what you’re about to do.

Here is a 12-row miniature of Thursday’s 60,000-row dataset. By eye, on paper, answer: (1) how many rows have temp_C > 80? (2) What is the mean rpm among only those rows? (3) Which test_phase has the higher average temperature?

That two-step — verify small, then scale — is the whole P3 + A1 partnership.
