Google Colab: a lab bench in your browser

Go to colab.research.google.com and sign in with your university Google account. Click New notebook. That’s the whole setup. You now have a notebook: a document made of cells, where each cell holds a bit of Python code you can run by pressing Shift+Enter (or the ▶ button).

Python runs on Google’s computers, not yours — that’s why there’s nothing to install. Your Chromebook, gaming rig, and six-year-old laptop are all equally powerful here.

Variables: giving numbers names

A variable is a name attached to a value, so you can use the value by its name:

g = 9.81        # gravitational acceleration, m/s^2
h = 3.0         # drop height, m

Everything after a # is a comment — a note for humans that Python ignores. Notice the comments carry the units. In this course, a number without units is a rumor.

The = sign here does not mean “equals” in the math sense. It means “store the value on the right under the name on the left.” This distinction will matter enormously, so here’s the line that looks insane to a mathematician but is everyday code:

count = count + 1

As algebra, nonsense. As an instruction — take the value stored in count, add 1, store the result back under count — perfectly sensible. Reading = as “gets” instead of “equals” will save you real confusion.

Some reading help: line 3 computes \(t = \sqrt{2h/g}\) — the fall time of a dropped object, which you met last week. So before running: \(2 \times 3 / 9.81 \approx 0.61\), and \(\sqrt{0.61} \approx 0.78\). Prediction: something near 0.78.

You should see 0.7820... — matching the hand estimate. Feel that little click of confirmation? That’s verification (standard A1), and it’s the feeling this course is built around. You didn’t trust the program because it ran; you trusted it because you predicted its behavior and it complied.

If you got an error instead — welcome to programming; see the next section.

This predict-then-run move is the single most important habit in the course. It’s how you’ll read AI-generated code, how you’ll debug, how class voting works, and how the final exam works. Running code without a prediction teaches you nothing; you’re just watching lights blink.

Errors are data, not disasters

Delete the h = 3.0 line and run the cell again. You’ll get an angry red block ending in something like:

NameError: name 'h' is not defined

Two things to know about errors, permanently:

They are normal. Professionals generate errors all day. The difference between a beginner and an expert isn’t fewer errors — it’s that the expert reads the message. The last line usually names the problem (NameError: you used a name nothing was stored under) and an arrow points at the guilty line.

They are the friendly failure mode. A program that crashes loudly is telling you where it hurts. The dangerous program is the one from last week’s reading — the one that runs happily and produces a wrong answer in a confident voice. You will come to prefer the crash.

Tip

Error message you can’t parse? That is a genuinely excellent use of an LLM: paste the code and the full error, and ask what’s wrong. Then — habit — verify the explanation makes sense before applying the fix. Junior collaborator, remember.

8 — not 2. Line 2 stored the value 8 under b; it did not create a live mathematical relationship “b is twice a.” When a changed afterward, b had no reason to care. Code executes top to bottom, once, each line acting on values as they are at that moment. If you predicted 2, you read = as algebra. Extremely common, now permanently fixed.

That misreading — treating a program like a set of simultaneous equations instead of a sequence of actions in time — is the most common beginner stumble there is, and you’ve just met and defeated it in four lines.
