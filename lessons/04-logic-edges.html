Logic & edge cases

Week 4 — read before Tuesday

This week the code learns to make decisions — and you learn that edge cases, the places where decisions get made, are where specifications go to die.

Think First

Recall

  1. Week 1, the robot sandwich: what happens to every question your instructions didn’t answer?
  2. Week 3: what did fall_time(3.0) assume about the sign of the input? What should fall_time(-3.0) do?

Look Ahead

  1. Is a negative flow rate an error, or just flow in the other direction?
  2. Would you rather a program crash loudly or continue quietly with a bad value?

Booleans: questions with yes/no answers

A boolean is a value that is either True or False. Comparisons produce them:

The = vs == confusion causes real bugs weekly, worldwide, at every experience level. Read == as “is it equal?” — a question — and = as “gets” — a command.

if / elif / else: branching

def battery_status(T):
    """Classify battery temperature T in Celsius."""
    if T > 60:
        return "SHUTDOWN"
    elif T > 45:
        return "warning"
    else:
        return "nominal"

Reading rule: conditions are checked top to bottom, and only the first true branch runs. Trace battery_status(50): is 50 > 60? No. Is 50 > 45? Yes → "warning", done — the else never even gets looked at. Now predict battery_status(60) — exactly 60. (Not greater than 60, so not shutdown: "warning". Is that what a battery engineer wants at exactly the shutdown threshold? That’s not a Python question. Hold that thought.)

Edge cases are specification questions wearing code costumes

Here is the deepest idea this week. Consider a flow-rate input of -3.0 L/min. What should the pool-fill function do?

  • Crash with ValueError("flow rate must be positive")?
  • Return a negative fill time and let the caller deal with it?
  • Interpret it as draining and compute time-to-empty?

Python has no opinion. All three are two lines of code. The decision is engineering — it depends on what the program is for, who calls it, and what failure costs. This is exactly the week-1 lesson coming home: an edge case is a gap in the spec, and something will fill the gap. Either you decide, or the AI’s statistical average of the internet decides, or physics decides at runtime. Pick the first one.

Important

When you prompt an AI for a function, your spec should answer the edge questions explicitly: “raise a ValueError for non-positive flow rates.” Watch what happens when you don’t: the AI picks one of the three behaviors, confidently, without telling you which.

Defensive functions

The professional habit — a function that checks its own inputs and fails loudly and usefully:

Live cell — now abuse it: change the flow to -3.0 and run. That error message, loud and specific, is what your functions owe their callers.

raise stops the program with your message. Compare the debugging experience: ValueError: flow must be positive, got -3.0 versus a silent negative fill time propagating into a report your boss reads. Loud failure is a gift to your future self. (Recall week 2a: you will come to prefer the crash.)

Preview: while, the conditional loop

T = 90.0
minutes = 0
while T > 40:          # keep going as long as this is True
    T = T - 2.5        # coffee cools 2.5 degrees per minute (crude model)
    minutes = minutes + 1
print(minutes)

Read it as “repeat until the condition breaks.” Predict the printed value (how many 2.5° steps from 90 down to 40 or below?) — the answer settles at Tuesday’s tables, not here — then notice the danger: if the loop body never changes T, the condition never breaks and the program runs forever. Every while loop is a small specification exercise: what guarantees this ends?

For the battery_status function above, commit on paper to its output for these four inputs: 44, 45, 61, and -40. Two are ordinary; two are edges. For each edge, add one sentence: is the function’s behavior correct, and what would you change in the spec? Thursday’s vote is on -40 — a temperature a Colorado battery will actually see — and then the edge-case hunt: tables get each other’s week-3 functions and try to break them with hostile inputs. Bring your meanest test cases.
